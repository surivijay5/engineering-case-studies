# Reusable Agentic UI Architecture

## Designing a Reusable Frontend Architecture for Multi-Turn AI Agents

### Overview

I helped design and implement a reusable frontend interaction foundation for multiple AI-assisted workflows inside an enterprise SaaS product.

The challenge was not simply displaying chatbot text.

The application needed to support:

- Streamed responses
- Structured interactive content
- Actions generated by AI workflows
- Multi-turn user input
- Conversation continuity
- Refresh/recovery behavior
- Coordination across frontend, agent host, backend, and tool layers

My work included the shared card/streaming foundation and helping establish elicitation as an explicit multi-turn interaction protocol rather than feature-specific screen state.

### The Problem

The product was introducing multiple agent-driven workflows.

A naive implementation would have created:

```text
Agent A → custom UI implementation

Agent B → another custom UI implementation

Agent C → another custom UI implementation
```

That would tightly couple each frontend implementation to a particular agent or backend tool.

Instead, we needed reusable interaction primitives that could support new workflows without rebuilding the rendering and action architecture each time.

### Core Requirements

The frontend needed to handle:

- Text and structured responses
- Cards and tabular data
- Incremental streamed messages
- Interactive actions
- Pending user input
- Conversation history
- Restored sessions
- Stale-state cleanup
- Backend-generated workflow progression

### My Role

I worked on the architecture and implementation across frontend and cross-layer contracts.

This included:

- Reusable card and streaming behavior
- Interaction/message contract design
- Elicitation continuity
- Frontend ↔ host coordination
- State behavior across multi-turn interactions
- Design/documentation used by engineering and product stakeholders

### Architecture

```text
                 User
                   ↓
           Agent experience
                   ↓
          Streaming messages
                   ↓
       Structured UI contract
          ↙       ↓       ↘
       Text      Cards    Tables
                   ↓
            User interaction
                   ↓
            Action dispatcher
                   ↓
          Agent / host layer
                   ↓
             Tools / APIs
                   ↓
          Next streamed state
```

The important design choice was that the frontend rendered **generic interaction structures**, not agent-specific implementations.

### Key Design Decisions

#### 1. Structured AI responses instead of text-only UX

Complex agent workflows often need more than conversational prose.

Users may need to:

- Select an item
- Review a table
- Confirm an operation
- Edit information
- Continue a workflow

So the frontend treated structured responses as first-class UI primitives.

#### 2. Decouple UI interaction from tool implementation

The frontend should not need to know which backend function or agent tool ultimately processes every action.

Instead, user interactions could be represented through shared action contracts.

```text
Rendered component
      ↓
User action
      ↓
action identifier + payload
      ↓
shared interaction path
      ↓
backend / agent determines execution
```

This reduced agent-specific frontend logic.

#### 3. Treat elicitation as protocol state

One of the more important design lessons was that waiting for user input in a multi-turn agent flow is not merely a local UI state.

The system must know:

- That an interaction is pending
- Which workflow it belongs to
- How subsequent input continues it
- What happens after refresh
- How stale state is cleared

The interaction therefore had to be treated as a **cross-layer protocol/state continuity problem**.

#### 4. Handle live state and restored state deliberately

Agent interfaces need to behave correctly both:

- During the live streamed interaction
- After the same interaction is reconstructed later

Those paths can expose different bugs.

This became particularly important during performance and concurrency validation.

### Outcome

The work established reusable interaction patterns rather than independent implementations for every agent.

The resulting architecture helped provide:

- Shared agent UI primitives
- Clearer frontend/host/backend boundaries
- Reusable card and streaming behavior
- A common model for multi-turn interactions

### What I Learned

The difficult part of building AI product experiences is often not connecting to an LLM.

The hard problems are:

- State
- Interaction contracts
- Partial responses
- Recovery
- Concurrency
- User control
- Separation between presentation and tool execution

Treating those as architecture concerns makes agent experiences much easier to extend and operate.
